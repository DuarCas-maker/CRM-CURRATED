# Promoción y reversa

Preparación local en worktree aislado; no modificar el WIP del frente Connect ni el coordinador. Publicar requiere revisar el paquete completo, catálogo SQL vigente y autorización del destino. Antes del SQL productivo: respaldo privado comprobable y catálogo/ACL de los nuevos RPC. No sustituir funciones vigentes ni repetir migraciones anteriores.

Destino autorizado: aplicación CRM en https://crm.finlabinc.com y su Supabase autoalojado en https://supabase.finlabinc.com. El runbook se preparó antes de ejecutar; resultados reales posteriores en release-progress.md y evidence/production-*.json. No cambiar destinos, infraestructura, variables ni modo operativo del worker.

Pasos propuestos, tras la autorización del paquete:

1. Verificar HEAD y WIP del coordinador y producción. Base local a34a08938cc637aa28b5176af31368cce30c554c. Los tres componentes modificados deben conservar sus hashes de base del manifiesto o conciliarse explícitamente. No incluir WIP ajeno de layout.tsx, crm.tsx o server/supabase.ts. Preparar un commit de release con solo los archivos del paquete y documentación, sin reset/stash/clean sobre otros frentes.
2. Ejecutar migrations/preflight.sql con la conexión autorizada al destino verificado. Es lectura de metadatos con timeout y rollback: no contiene filas de negocio ni secretos. Revisar firmas, columnas, RLS, triggers de campañas y hashes del crm_command/brand guard actuales, incluidos cambios posteriores a052. Cualquier colisión con los cinco nombres nuevos detiene la aplicación; no usar CREATE OR REPLACE para sortearla. La prueba local con B2 no sustituye esta conciliación.
3. Registrar referencia y prueba de un respaldo privado restaurable de Supabase, y versión anterior de app. Mantener backup/credenciales fuera del repo y la respuesta. Asignar el identificador de migración con el coordinador; no reutilizar048–052 ni aplicar otra vez esos scripts.
4. Aplicar exclusivamente migrations/up.sql con psql -X -v ON_ERROR_STOP=1 -f <ruta-up-autorizada> mediante el canal vigente. El archivo es transaccional. Son cinco funciones nuevas, cuatro RPC expuestos a authenticated y un helper sin EXECUTE para roles API. No altera tablas, políticas, datos históricos, el comando público o funciones de entrega. Verificar hashes, search_path vacío, propietario, ACL y recarga de caché PostgREST; no probar mutaciones con usuarios reales.
5. Ejecutar checks del candidato integrado y publicar ese commit por el mecanismo de release del CRM. No modificar el worker ni reiniciar Supabase para esta entrega. No cambiar dependencias, env, CSP, OAuth, DNS o volúmenes. La base puede adelantarse a la app; una app adelantada al SQL devuelve503 y nunca usa la audiencia global.
6. Comprobar salud del release, acceso sin sesión denegado y pantalla con sesión/MFA. El smoke de publicación se limita a lecturas. No cargar un Excel real, aprobar Bouncer, activar/programar campañas ni enviar correos como parte del smoke. Para una prueba real posterior se requiere un lote y presupuesto elegidos explícitamente por el usuario.

Criterio de éxito: versión de app identificada y saludable, cinco funciones con hashes/ACL esperados, navegación Campañas → Crear campaña correcta y ausencia de cambios operativos ajenos. Registrar versión, aprobador, fecha y evidencia en verification.md.

Reversa: publicar la versión anterior de app conservando commits ajenos; tras comprobar que los hashes de las cinco funciones siguen perteneciendo al paquete, retirar solo esos RPC con psql -X -v ON_ERROR_STOP=1 -f <ruta-down-autorizada>. Si existe drift no retirar funciones desconocidas. No borrar campañas o lotes creados: sus snapshots y métricas siguen funcionando mediante el motor anterior. Las campañas ya activadas requieren una decisión operativa explícita de pausa, no se cambian por revertir la interfaz. No hay backfill ni tablas nuevas.

Riesgo material: faltaba el aislamiento por lote en el comando anterior y el trigger de marca exige contexto transaccional al fijar la audiencia. Ambos se cubren por el RPC y las regresiones locales; el catálogo post052 y Auth/PostgREST reales todavía requieren validación antes de promoción. Build de contenedor y despliegue no se ensayaron en este incremento.
