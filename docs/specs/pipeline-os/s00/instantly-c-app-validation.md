## Implementación

- [047](../../../../supabase/migrations/047_instantly_webhook_control_leases.sql): tabla técnica con RLS y sin acceso directo para anon/authenticated/service_role; tres RPC exclusivas de backend y helper privado. Solo se almacena SHA-256 del token. Actor activo/superadmin, trial/nonce, plazo y cuotas se validan en cada operación. La reserva durable sobrevive a una transición rechazada; arm/close/revoke se intentan una vez. No modifica 046, campañas, leads, mensajes, jobs o worker.
- [Contrato](../../../../src/lib/server/instantly/control-contract.ts) y [rutas](../../../../src/lib/server/instantly/control-endpoints.ts): flag apagada devuelve 404 antes de crear cliente; grant exige sesión/MFA/origen y actor del servidor. API de control limitada al ensayo, Bearer, JSON acotado, sin redirects, respuestas no-store y errores sanitizados. La autenticación de grant limita su transporte a cuatro consultas al Supabase configurado; el control ejecuta un único RPC por petición.
- [Control en Integraciones](../../../../src/components/instantly-trial-control.tsx): superadmin activo importa la autorización final, revisa destino/ventana/presupuesto y realiza un único intento. Credencial efímera descargable en `.env`, metadata separada; ninguna cookie, contraseña o clave de servicio se entrega al ejecutor. El token no entra en el manifiesto JSON, estado de negocio o logs.
- [Puente](../../../../scripts/pipeline-os/s00-instantly-control-bridge.ts), [ejecutor](../../../../scripts/pipeline-os/s00-instantly-c-app.ts), [archivos](../../../../scripts/pipeline-os/s00-instantly-c-app-files.ts) y [CLI explícita](../../../../scripts/pipeline-os/s00-instantly-c-app-cli.ts): mismo journal autoritativo, nueva envoltura v9 con estado proveedor v7/v8 original y bloque de control independiente. Reserva antes de HTTP, polling cada 10 segundos como mínimo y hasta 12 observaciones normales. Cierre → lectura final congelada → revocación → comprobación 401. Un reinicio con estado running no reanuda automáticamente.

El callback real inyecta siempre la admisión 047: máximo 16 admisiones por lease, antes de persistir. El cierre SQL y la admisión bloquean lease y trial en el mismo orden. Un callback previamente admitido con revisión antigua falla su CAS tras el cierre y no altera el snapshot final. La fábrica histórica conserva su dependencia opcional para compatibilidad, sin eludirla en la ruta publicada futura.

### Diagnósticos resueltos durante QA

1. La primera ejecución SQL reprodujo `column reference t.id is ambiguous`: los aliases de JOIN coincidían con variables PL/pgSQL. Se usaron aliases distintos en issue/execute/admit; lifecycle y roles lo protegen.
2. La simulación del ejecutor falló en stage 1 por perder el contexto del reloj inyectado. El adaptador conserva sus métodos mediante closures; el flujo completo pasa con reloj ficticio.
3. El barrido de escrituras detectó dos peticiones de limpieza después de una persistencia fallida. Ahora toda persistencia posterior rechaza inmediatamente por almacenamiento incierto; no se permite gastar proveedor/control para intentar compensar un diario no confiable. Se conserva el estado para recuperación específica.
4. La primera copia de QA omitía rollbacks/install SQL históricos y el PDF ficticio de Composio: 24 fallos ENOENT. Se completó la copia pública, sin modificar ni relajar pruebas del producto. La primera compilación falló al crear junctions de Turbopack en Windows; se repitió con permisos locales suficientes en la copia aislada, manteniendo variables ficticias y conexiones bloqueadas.
