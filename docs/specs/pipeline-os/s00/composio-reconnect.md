## Descubrimiento y decisión S00-B-ADR01

La observación anterior terminó en **60 peticiones acumuladas** (37 históricas+23 nuevas), dos muestras y relecturas correctas. Quedan17 bajo el techo anterior77, vinculadas a aquel alcance. Composio ya demostró transporte; falta pérdida y recuperación de acceso. Los scripts actuales son de lectura/envío controlado y no soportan revocación ni alta de conexión. `s00-composio-common.ts` restringe rutas/métodos y espera HTTP200; no se reutilizará como transporte de mutaciones sin diseño explícito de nuevas rutas y HTTP201.

Inspección local sin env/API: los dos buzones son distintos, pero **comparten `user_id` en Composio**. Ese propietario no permite seleccionar el correo. Para todo paso se usará ID de conexión explícito y huella de perfil Gmail. No consultar o modificar todas las cuentas de un usuario para intentar desconectar M1. Se propone **M1 como objetivo y M2 como control**, supuesto reversible antes de ejecutar.

Se propone revocación real del acceso de M1 y nuevo consentimiento OAuth del mismo correo. Una pausa INACTIVE/ACTIVE no verifica recuperación de un grant revocado. No se usará DELETE como atajo. El endpoint antiguo status está deprecado y puede afectar triggers; refresh también está deprecado y no acredita validez de credenciales. En vez de cambiar stack o incorporar SDK, se planifica HTTP v3.1 explícito y acotado, reutilizando parsing, timeouts y persistencia existentes con las extensiones mínimas.

Revocar no tiene un deshacer que reponga los tokens anteriores: la recuperación requiere que la persona vuelva a autorizar Gmail. La operación de proveedor es best effort. Un rechazo de ejecución del ID antiguo prueba que Composio dejó de utilizar esa conexión; no demuestra por sí solo invalidación global de todos los tokens Google. No se extraerán tokens para intentar esa demostración.

## Contratos oficiales consultados

Consultados el 26 de octubre de 2026, sin llamadas autenticadas:

- [Revocación v3.1](https://docs.composio.dev/reference/api-reference/connected-accounts/postConnectedAccountsByNanoidRevoke): `POST /api/v3.1/connected_accounts/{id}/revoke`. HTTP200 describe conexión REVOKED y categorías de tokens revocados; 400/409/500 tienen significados distintos. No inferir éxito desde un timeout. Esta ruta no elimina el registro.
- [Enlace OAuth v3.1](https://docs.composio.dev/reference/api-reference/connected-accounts/postConnectedAccountsLink): `POST /api/v3.1/connected_accounts/link`, campos documentados `auth_config_id`, `user_id`, `alias` opcional; HTTP201 con `connected_account_id`, `redirect_url`, `expires_at` y `link_token`. No inventar `allow_multiple` en el body REST. Se omitirá callback personalizado; se conserva el flujo hospedado existente.
- [Guía de ciclo de vida](https://docs.composio.dev/kb/guide/platform-connected-accounts): el enlace requiere consentimiento humano, tiene duración corta (~10min) y el estado ACTIVE no sustituye una prueba de identidad/acceso. No utilizar refresh deprecado para verificar tokens.
- [Implementación oficial de link](https://github.com/composiohq/composio/blob/next/python/composio/core/models/connected_accounts.py) y [guía de migración](https://docs.composio.dev/docs/auth-configuration/migrating-initiate-to-link): el SDK realiza un listado previo para controlar duplicados y puede habilitar múltiples conexiones. El REST link documentado no incluye ese flag; no añadir SDK y sus llamadas implícitas. Con dueño compartido, una cuenta ACTIVA del mismo user_id no equivale a duplicado del mismo Gmail. Cada candidate se verificará por perfil.
- Se conservan los GET de conexión/config y el proxy Gmail profile/threads metadata ya comprobados en [S00-A](composio-auto-receive.md). Para una reconciliación extraordinaria, solo [listado filtrado](https://docs.composio.dev/reference/api-reference/connected-accounts/getConnectedAccounts), hasta una página y límite20, con toolkit Gmail, propietario y auth config originales. No continuar si la página no permite una identificación inequívoca.

El enlace y link_token son secretos temporales: no registrar la respuesta completa, URL OAuth o tokens en Git, logs o reporte público. La URL se entrega solo al operador del ensayo por un canal privado/controlado, no a clientes. La autenticación Gmail la completa la persona en Google; no se solicita ni automatiza su contraseña. No usar tokens enmascarados de los GET como credenciales.

## Procedimiento propuesto

1. **Preflight (7 consultas):** uso inicial1, Auth Config1, GET M1/M2 dos, profile por proxy M1/M2 dos, baseline metadata del hilo conocido M1 una. Verificar cuentas distintas y perfiles originales, scope readonly, config propia, presencia de IDs de mensajes del ensayo anterior y ausencia de actividad de envío en este ejecutor.
2. **Preparar reconexión (1 POST):** crear una sesión link para propietario y Auth Config originales, alias único de este intento. Validar HTTP201, ID candidate distinto de M2/origen, URL HTTPS hospedada, expiración y respuesta mínima. No imprimir secretos. Con menos de tres minutos de vigencia útil, no revocar; no crear enlaces en bucle. Se comunica que la siguiente acción corta temporalmente M1, con recuperación ya preparada.
3. **Desconectar y comprobar (4 peticiones):** reservar la mutación antes de HTTP y revocar M1 una vez; GET de M1 antiguo para conciliar REVOKED; una única lectura proxy profile con ese ID debe rechazar el acceso; profile de M2 debe seguir correcto. El error esperado debe corresponder a conexión revocada/no utilizable, no a key global inválida. Si el ID viejo aún funciona, registrar fallo y no repetir la revocación a ciegas. Si M2 pierde acceso, cortar las pruebas y priorizar recuperación manual.
4. **Reautorizar (persona + 1–4 GET):** avisar al operador para abrir el enlace vigente y escoger exactamente el Google M1 original. No enviar correo de prueba. Después de que confirme completar OAuth, consultar el candidate; si sigue inicializando, otras lecturas a los15,30,60s desde esa confirmación, máximo cuatro. No hay polling continuo durante el login humano, ni SDK wait con llamadas ocultas. Si el proyecto exige un callback verifier, no aprobarlo automáticamente: ese contrato está fuera de la prueba y debe prepararse antes de revocar.
5. **Verificar recuperación (4 lecturas):** profile por proxy del candidate debe coincidir con la huella Gmail M1, además de user_id/Auth Config originales; leer metadata del mismo hilo M1; repetir esa lectura y comprobar que el conjunto baseline conserva IDs y no añade eventos duplicados; profile M2 final correcto. El ID Composio nuevo puede cambiar, los IDs de mensajes Gmail y el histórico deben conservarse. Una identidad M2 u otra cuenta nunca se enlaza como M1 aunque ACTIVE sea true.
6. **Cierre (1 consulta):** uso final y reporte sanitizado con estado y contadores. Conservar los IDs antiguos y nuevos como trazabilidad privada. Un nuevo binding se acepta solo después del perfil/histórico verificados, con estado operativo pausado; no reactiva envíos o campañas. Verificar locks liberados y que no queda proceso activo.

Las pruebas de error real solo son la revocación autorizada y el profile deliberadamente rechazado; el resto de errores extremos se simulan offline. Una revocación sin restauración verificada es una prueba incompleta, nunca un cierre exitoso. El consentimiento y las pantallas del navegador no tienen un número fijo de solicitudes de proveedor; el presupuesto siguiente cuenta solo intentos HTTP que inicie nuestro ejecutor hacia Composio, igual que en S00-A.

## Diseño técnico y recuperación

Planificar un ejecutor S00-B por fases explícitas `prepare → revoke → await_auth → verify → completed/recovery_required`, offline por defecto. Nuevas rutas de mutación tipadas y limitadas a M1/candidate, sin ampliar el helper general a PATCH/DELETE arbitrarios. HTTP201 solo para link y200 para revoke; redirecciones HTTP automáticas prohibidas en el ejecutor. El browser OAuth es un flujo humano separado.

Journal privado propuesto `.local/pipeline-os/s00-composio-reconnect.json`, con fuente del ledger S00-A60, huellas de configuración/destino, estados, IDs exactos, eventos deduplicados, llamadas reservadas y controles de identidad. Locks de origen/observación/reconexión en orden fijo, sin tocar journals terminados. El último ledger será la fuente autoritativa; nunca reutilizar saldos de runners anteriores.

El binding lógico M1→connected account candidate es independiente del ID de transporte antiguo y se acepta atómicamente tras validación. Auth Config ID se conserva; el nuevo Connected Account ID, si cambia, solo corresponde a M1. No ponerlo en ambas variables ni modificar M2. No editar env automáticamente o actualizar fingerprints históricos: el nuevo binding y lineage se guardan primero en el journal privado; un ajuste posterior de configuración se hace explícitamente en el alcance de ejecución/S02. Las claves pueden necesitar otra política de permisos; no exigir la huella de la antigua API key si se autorizó rotación, sí comprobar proyecto/Auth Config/cuentas y registrar la nueva huella de sesión.

Rollback: no se pueden recuperar tokens revocados. La compensación es terminar OAuth del mismo Gmail y verificar perfil/hilo, preservando el binding anterior como histórico. Si la identidad resultante es otra, no activarla para M1 ni revocarla/borrarla automáticamente; detener y corregir por la vía humana dentro de la reserva disponible. Una pausa INACTIVE/ACTIVE, token renovado, grant nuevo y binding nuevo son estados diferentes en el reporte. No se marca la prueba como exitosa con solo un HTTP200 o ACTIVE.
