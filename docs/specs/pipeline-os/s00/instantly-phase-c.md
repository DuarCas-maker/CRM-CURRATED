## Diseño y decisión INS-C-ADR01

### Incremento de implementación autorizado — 29/10/2026

El usuario solicita implementar ejecutor/receptor y probarlos offline, conservando43 y sin APIs/publicación/envíos. La clarificación1→A continúa vigente; no quedan decisiones de negocio nuevas para este incremento. Se implementaron INS-C-T02/T03/T04, sin adelantar T05/T06. El receptor será un handler Request/Response inyectable, sin listener ni adaptador público iniciado al importar. Stores separados para recibos y contador, con locks independientes y persistencia atómica; el recibo no consume ni reemplaza el contador API. El secreto de header y la clave HMAC local de correlación se resolverán solo durante una futura ejecución desde INSTANTLY_S00_WEBHOOK_SECRET e INSTANTLY_S00_WEBHOOK_DEDUP_KEY (64 caracteres hexadecimales cada una,≥32 bytes), vinculadas por hash al manifiesto privado; preview/status/replay no leen env. La referencia de payload seguirá el ejemplo oficial anonimizado, no datos de clientes.

Para distinguir GET404 esperado de otros HTTP4xx sin relajar A/B, se añadirá una entrada de transporte exclusiva de webhooks C sobre el bounded transport actual. El campo de status HTTP se conservará solo como metadato numérico del error interno; el allowlist A/B y sus códigos permanecen. C permite exclusivamente GET workspace/plan/campaña propia/hooks/logs, POST hook/test único y DELETE hook propio. Ninguna ampliación habilita send/activate/PATCH.

### Preparación del receptor, aún sin infraestructura elegida

Reutilizar runtime y validadores del paquete S00. Proponer un handler independiente y testeable con request/store/clock inyectados, sin incorporar una nueva ruta pública en la app o arrancar servicios ahora. Su adaptador HTTPS y alojamiento se decidirán al preparar el endpoint propio, con autorización específica si exige infraestructura. No usar un collector de terceros que almacene payloads de leads, ni copiar credenciales al navegador. La falta de URL pública no bloquea implementación/QA offline, pero bloquea ejecución real C.

Manifiesto privado futuro: versión de protocolo, source43Hash, bindings de manifiesto B/scope/clave/workspace/campaña, URL HTTPS dedicada con identificador de ensayo no secreto, nombre/nonce propios C, `event_type=reply_received`, ventana acotada, referencia al secreto y límites. Generar un secreto nuevo de≥32 bytes aleatorios; no reutilizar API key. El destino no lleva secretos en query/userinfo/fragmento ni redirects; autorización y logs deben ocultar header y ruta privada. Confirmar control del dominio/receptor, ausencia de cargos adicionales y ausencia de logging de cuerpos en proxy/alojamiento antes de suscribir. No se pide ni prepara ningún secreto durante esta planificación.

Autenticación callback: header `X-S00-Webhook-Token` dedicado, comparar en tiempo constante con longitudes seguras; comprobar método POST/content-type JSON/tamaño/schema. Validar tipos de campos conocidos y descartar campos extra tras análisis en memoria. La allowlist persistida solo contiene nonce local, tiempo local, flags de autenticación/contexto/schema, digest privado para replay y resultado técnico; nunca contenido de correo o lead. IDs requeridos para correlacionar logs se mantienen privados. No almacenar raw body ni headers completos.

El receptor se arma exclusivamente para un único test pendiente y una ventana de120s. El runner registra intención durable antes del POST test; el primer callback válido se guarda como evidencia tentativa, no como lead respondido. Un duplicado idéntico devuelve2xx solo si ya existe el recibo durable; un segundo payload distinto queda en cuarentena. Dedup técnica por digest HMAC local del body con clave dedicada al ensayo, no por email/asunto/timestamp ni como identidad comercial. Reinicio carga recibo antes de admitir otro y no repite test. Persistencia por archivo privado atómico con lock; disco lleno/fallo/lock ajeno no confirma entrega. Limitar a16 recibos/metadatos de entrega por ensayo; exceso devuelve429 sin registrar payloads. No hay escrituras de CRM, correo saliente o decisiones de negocio.

Contexto workspace/campaña/event_type correcto permite `contextValidated=true`. Un test de proveedor con datos de ejemplo ajenos puede acreditar **solo transporte sintético autenticado**, si concuerdan URL/ventana/intención única y resultado del POST test; contexto falso/ausente queda explícitamente en cuarentena y no cuenta como evento de la campaña. Sin esa correlación suficiente, estado parcial. Token válido no demuestra origen criptográfico del proveedor: se acredita conocimiento del secreto por el canal controlado, no firma HMAC de Instantly. Callback tardío tras cierre no reactiva el ensayo ni genera negocio.

### Fallos, conciliación y compensación

- Retry solo lectura ante red/timeout/429/5xx, máximo uno por operación y R3 global; no retry401/402/403,4xx permanentes, redirects, schema o identidad. Si falta evidencia de cupo o llega402, parar sin actualizar plan. Mismo transporte de8s/2MiB; ningún SDK con tráfico oculto.
- POST create/test y DELETE se intentan como máximo una vez cada uno. Create incierto: una consulta de listado filtrado por campaña/evento, comparación exacta URL/nombre/nonce, resultado único completo y propio; no cursor abierto/múltiples/sin coincidencia. Si no se resuelve, `cleanup_required` sin segundo create o DELETE de recurso no identificado.
- Test incierto: contrastar recibo propio durable y logs dentro de R; no volver a dispararlo. Si no hay prueba suficiente, resultado parcial/fallido. Los logs de tests no están garantizados por el contrato publicado; ausencia de log no implica automáticamente fallo de transporte ni autoriza provocar un evento real.
- DELETE incierto: GET propio dentro de R/H;404 demuestra ausencia,200 significa limpieza pendiente, otras respuestas no acreditan eliminación. No repetir DELETE. Nunca eliminar un webhook preexistente o con identidad/propiedad dudosas.
- Tras cualquier fallo elegible con hook propio identificado y todavía no eliminado, usar H para retirar ese hook y verificarlo, incluso tras cancelación humana. No gastar H en logs/diagnóstico. Ante fallo de identidad/auth o persistencia incierta, detener y reportar limpieza no comprobada; no encadenar escrituras ciegas. Conservar receptor cerrado para negocio, evidencia e ID privado para recuperación posterior específica.
- Drift de campaña bloquea el test/continuación, no PATCH/pause de campaña. C no tiene permiso de reparar campañas, añadir remitentes, borrar leads o reconfigurar B. Se informa estado observado y no se certifica pausa final si no se comprobó.
